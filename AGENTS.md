# go-hubspot

Unofficial Go client for the HubSpot API, generated from HubSpot's per-API OpenAPI documents, merged into one spec. If you only want to use the client from an agent, read [.agents/skills/go-hubspot/SKILL.md](.agents/skills/go-hubspot/SKILL.md) instead; this file is about changing the code.

## Architecture

The code is almost all generated. `gen.go` drives it with `go generate`:

1. `scripts/fetch-spec.sh` reads HubSpot's public spec index (`https://api.hubspot.com/public/api/spec/v1/specs`), downloads every document of API version `2026-03` and merges them with `scripts/merge-specs.jq` into `api/openapi.json`.
2. `scripts/patch-spec.sh` writes `api/openapi.patched.json`: it defines the `HubDbTableRowV3Wrapper` schema the HubDB document references but never defines, and types the two expression union fields (`PropertyDefinition.calculationExpression`, `RollupExpression.conditionalExpression`) as free-form objects, dropping the expression schemas only they reach.
3. `go tool oapi-codegen --config=config.yaml` writes `client.gen.go` (models and client, `number` mapped to `float64`).
4. `scripts/split-gen.sh` splits it into `client_NNN.gen.go` files of about 20,000 lines and runs goimports on each.

## Stack

- Go 1.26.10, one package `hubspot` at the module root.
- oapi-codegen v2 and golangci-lint as `go tool` dependencies; `github.com/oapi-codegen/runtime` at runtime.

## Layout

- `gen.go`, `config.yaml`: generation steps and oapi-codegen config.
- `client_NNN.gen.go`: generated client, never edited by hand.
- `client_test.go`, `example_test.go`: httptest-based tests and the README example.
- `scripts/`: spec fetch and merge, spec patch, split, lint and security scan scripts.
- `api/`: the downloaded spec, gitignored.
- `vendor/`: committed, regenerated by `make dep`.

## Dev workflow

Everything runs in the `Dockerfile.dev` image. You need Docker and Make.

```bash
make dep       # go mod tidy + go mod vendor
make generate  # fetch the spec and regenerate
make lint      # shellcheck, shfmt, go fix, golangci-lint
make test      # go test -race
make sec       # gitleaks, govulncheck, semgrep
```

## Project-specific landmines

- Method names embed the API version date from the path (`...202603...`). A new spec can rename every method, so check tests, the example, the README and the skill after `make generate`.
- The generated code is close to 300,000 lines. `make lint` takes several minutes even split; do not merge the files back.
- The merge is deterministic and fails rather than guess. Same-named schemas that differ in structure (descriptions and examples aside) keep the name for the variant most documents use; the others get the PascalCase title of their first document as a prefix (`CMSMediaBridgeProperty`). An operation several documents define must match everywhere; the copy with the shortest operationId wins, which decides the method name. A new spec can move these renames, so check the generated diff.
- The API version is the `API_VERSION` constant in `fetch-spec.sh`. Moving to a new version renames every method.
- Do not fetch from the HubSpot-public-api-spec-collection GitHub repository: its README says it is not licensed for external use. The public spec index API is the source.
- `.github/workflows/regen.yml` regenerates the client every day and releases the result. When the checks fail, Claude edits the repository to fix them, but a fix may not touch the paths listed under `fix_protected_paths` in that workflow: the workflows, the Makefile, `AGENTS.md`, `.agents/rules/`, the lint, security and spec download scripts and their configs. A problem that needs a change there fails the run and needs a manual fix.
